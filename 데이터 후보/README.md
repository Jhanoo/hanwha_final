## 평가와 자체 데이터

[FunctionChat-Bench](05_FunctionChat_Bench.md)는 한국어 도구 사용 평가 자료로 유지하고 학습에는 넣지 않는다. 자체 IT 대화는 실제 근거와 tool 계약에 맞춰 검수한다.

우리 티켓은 IT 장애·지원 요청을 접수하고 담당자가 처리하는 업무 기록이다. 담당자 배정은 사용자 요구지만 현재 코드에 해당 API/필드가 없으므로 가상 할당 샘플은 설계 예시로만 남긴다.

## 시작 순서

1. 저장소 계획대로 API 모델+prompt+RAG 기준선을 먼저 만든다. 이번 조사에서는 모델을 호출하지 않았다.
2. 평가 사례 60건(개발 40, holdout 20)을 먼저 고정하는 저장소 계획을 따른다. 더 큰 평가셋은 확장 단계다.
3. Console-AI 문의 선별 및 한국어 재라벨링으로 분류·요약 자료를 준비한다.
4. 공식 근거로 추가 질문→검색→미해결→초안→직원 확인→생성 결과 안내 대화를 검수한다.
5. 반복적인 행동 오류가 남으면 100~200건 pilot, 이후 300~1,000건 SFT를 검토한다. 수량은 최적값이 아닌 제안이다.
6. 실제 담당자 목록·배정 정책·API 확정 후 할당 학습 자료를 추가한다.

## 공통 주의점

변하는 기술 지식은 RAG, 질문·분류·요약·도구 선택은 행동 튜닝, 권한·승인·우선순위·멱등성은 서버가 책임진다. 공개 priority/queue를 사내 배정 정책으로 복사하지 않는다. 알 수 없는 영향/원인을 정답에 만들어 넣지 않는다.

원본·번역·패러프레이즈·같은 생성 템플릿은 같은 분할 그룹으로 관리한다. 원본 URL·revision·변환 이력과 합성 여부를 기록한다. 샘플 발췌는 완전한 학습 레코드가 아니다. 공식 문서 공개 여부와 재배포·학습 허가는 구분한다.

## 실행 및 검증 범위

저장소 정적 검토, 공개 데이터 카드 확인, 유지한 4개 후보의 첫 100행 조회를 수행했다. 규모·출처·검사 기록과 샘플 구조를 저장했다. 전체 학습셋 정제, 라벨 전수 검수, 앱 실행, DB 연결, embedding 색인, 모델 호출, SFT, 실제 성능 평가는 미실행이다. GitHub에는 문서를 푸시하지 않았다.
