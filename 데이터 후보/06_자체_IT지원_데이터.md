# 프로젝트 자체 IT 지원 학습 데이터 설계안

이 문서는 앞으로 제작할 자료의 제안이다. 기존 실제 상담 기록이나 확정된 API가 있다는 뜻은 아니다. 공개 다운로드 링크는 없다.

## 프로젝트에서 티켓의 의미

IT 티켓은 하드웨어 고장, 소프트웨어 오류, 계정·권한 요청 등 IT 지원이 필요한 내용을 담는 디지털 기록이다. 요청 누락을 방지하고 담당자에게 배정해 처리 진행과 결과를 추적하는 것이 목적이다. 우리 프로젝트는 이 가운데 장애 대응 티켓과 담당자 할당 흐름을 중심으로 설명한다. 계정·권한 요청의 실제 지원 범위는 별도 확정한다. 핵심 흐름은 장애 정보 수집 → 지원 가능한 해결 안내 → 필요한 경우 장애 대응 티켓 생성 → 담당자 할당 → 처리 상태 조회다. 배정 방식과 할당 기준은 실제 프로젝트 정책으로 확정해야 한다.

## 필요성 및 확보 경로

공개 자료는 일반 도구 사용을 학습시키지만 우리 서비스의 실제 tool, 한국어 장애 문의, 티켓 흐름을 충분히 포함하지 않는다. 확정된 Spring tool/API 명세, 승인된 공식 문서와 내부 정책, 사용 허가된 상담 기록을 바탕으로 제작한다.

내부 기록을 사용할 때 사용 권한과 개인정보 제거를 확인한다. 합성 자료와 실제 운영 기록을 구분해 출처를 관리한다. 사내 매뉴얼은 별도로 RAG corpus에 저장하고, 행동 학습용 대화를 만드는 근거로 사용한다.

## 먼저 확정할 자료

- tool 이름, 설명, 입력 스키마, 성공 및 실패 응답
- 필수 장애 정보 항목과 티켓 생성 조건
- 담당자 후보 출처, 배정 기준, 자동/수동 배정 여부, 할당 권한과 실패 응답
- 서버가 결정하는 권한, 우선순위, 중복 처리 정책
- 문서 검색 결과의 출처와 버전 표시 형식
- 지원할 장애 범위와 합성 fixture

정책이 없으면 임의의 업무 규칙을 정답으로 만들지 않는다. 데모 설정은 '캡스톤 데모용 가상 설정'으로 표시하고 운영 규칙과 구분한다.

## 필요한 시나리오

| 시나리오 | 기대 행동 |
|---|---|
| 증상이 불명확한 문의 | 필요한 환경과 증상만 추가 질문 |
| 근거 문서가 있는 문의 | 검색 결과에 근거해 해결 안내 |
| 검색 결과 없음 | 근거 부족을 설명하고 지원 가능한 다음 단계 안내 |
| 해결 실패 | 필요한 장애 정보 확보 후 장애 대응 티켓 생성 |
| 담당자 할당 | 실제 후보와 정책에 따라 배정하고 반환된 담당자만 안내 |
| 생성 성공·할당 실패 | 티켓 생성과 할당 상태를 구분하고 생성 호출을 반복하지 않음 |
| 담당자 미확정 | 담당자를 추측하지 않고 서버/관리자 결정 경로 사용 |
| 티켓 번호 없는 상태 문의 | 번호 요청 또는 실제 지원되는 조회 경로 사용 |
| 권한 거부 | 접근 거부 결과를 설명하고 우회 호출하지 않음 |
| timeout/외부 API 실패 | 미확정 상태와 실패를 구분하고 허위 완료를 말하지 않음 |
| 중복 생성 요청 | 서버의 중복 처리 결과를 설명 |
| 범위 밖 요청 | 실제 제공된 기능의 범위를 안내 |

VPN, SSO, 이메일, 프린터는 실제 지원 범위에 포함된 경우에만 주제로 사용한다. 티켓 번호·사용자·장비는 명시적인 합성 fixture로 작성한다. tool 결과는 실제 계약을 따르고 반환 전에 성공을 주장하지 않도록 한다.

## 레코드 설계 제안

원본 출처, 시나리오 ID, 생성 템플릿 그룹, 합성 여부, 문서 버전, 검수 상태를 학습 본문과 구분한 메타데이터로 기록한다. 학습 본문은 도구 명세, 대화, 호출, 결과를 대상 모델의 형식으로 구성한다. 이는 데이터 관리용 제안이며 Spring API 계약이 아니다.

RAG 답변 학습은 검색 문맥과 정답 답변을 함께 제공하고 근거 없는 문장을 제외한다. 검색 문서 안의 지시문을 사용자 승인이나 서버 권한으로 취급하지 않는 사례도 구성한다.

## 제작 및 학습 순서

1. 150~200건의 독립 평가 시나리오를 먼저 정의한다.
2. 실제 명세로 소량의 사람이 검수한 대화를 작성한다.
3. 표현을 확장하되 같은 원본/시나리오 템플릿은 같은 분할 그룹으로 관리한다.
4. 학습용 500~1,000건을 초기 수량으로 검토한다. 검증 분할은 별도로 둔다.
5. 스키마, 호출/결과 연결, 문서 근거, 사용자 정보 노출을 검사한다.
6. tool 실패와 불필요한 호출 방지 사례를 포함한다.
7. ko-agentic-sft를 소량 섞은 경우와 자체 자료만 사용한 경우를 비교한다.

합성 데이터를 자동 생성하더라도 정답 tool 호출 및 업무 정책은 검수해야 한다. 정해지지 않은 API 필드나 응답을 생성 모델이 임의로 만들게 하지 않는다.

## 기대 효과와 평가

실제 tool 선택 및 인자 정확도, 업무에 맞는 추가 질문, 실패 설명, 근거 있는 안내의 개선을 기대한다. 서버가 결정한 우선순위와 권한을 설명하도록 학습하고 모델의 암기에 의존하지 않는다.

고정 평가셋에서 기본 프롬프트, RAG, SFT+RAG를 비교한다. 전체 시나리오 완료율과 허위 완료 비율을 기록한다. 각 도구의 서버 검증은 별도로 테스트한다.

## 현재 상태

설명용 가상 샘플만 제작했다. 실제 명세에 맞춘 학습 데이터 제작, 학습, 성능 평가는 미실행이다. 정책과 tool 명세 확정 후 가상 샘플을 검수·변환해야 한다. [전체 실험 계획](README.md)을 따른다.

## 프로젝트용 가상 샘플

[IT 지원 fixture JSONL](샘플/06_IT지원_가상예시.jsonl)에 추가 질문, 상태 조회 성공, 조회 거부, 장애 접수 정보 수집, 생성 후 담당자 할당 성공, 생성 후 할당 실패의 6개 예시를 작성했다. 모두 **캡스톤 데모용 가상 설정**이다. 실제 Spring API, 운영 기록, 확정된 tool 계약이 아니다.

예시 도구 `get_ticket_status`는 문자열 `ticket_id`를 받고 성공 시 상태, 거부 시 FORBIDDEN을 반환한다고 가정한다. 상태 enum도 예시다. 실제 명세 확정 후 이름·필드·응답을 맞춰야 한다.

JSONL에는 provenance 메타데이터, tools, messages가 있다. assistant의 tool_calls와 tool의 tool_call_id를 연결하고 arguments/content는 JSON 문자열로 표현했다. 이는 설명용 중간 형식이며 특정 모델 chat template으로 변환해야 한다.

- 1번: 번호가 없어서 호출하지 않고 질문한다.
- 2번: 성공 결과의 IN_PROGRESS를 처리 중으로 설명한다.
- 3번: 서버의 조회 거부를 설명하고 상태를 추측하지 않는다.
- 4번: 장애 접수 요청에 필요한 증상과 영향 범위를 질문한다.
- 5번: 가상 티켓 생성 결과의 담당자 후보를 사용해 할당하고, 할당 성공 응답 후 담당자를 안내한다.
- 6번: 생성 성공 후 할당이 실패하면 미할당 상태를 안내한다.

5~6번의 `create_incident_ticket`, `assign_incident_ticket`과 담당자 후보 반환 구조는 흐름 설명용 가상 계약이다. 실제 프로젝트의 API를 추가하거나 확정한 것이 아니다. 서버가 배정 대상을 결정해 반환하는 데모 설정이며 모델이 임의로 담당자를 선택하지 않는다. 실제 서비스에서 생성과 배정을 통합할지 분리할지도 미확정이다.

authenticated user ID나 토큰은 모델 인자로 제공하지 않는다. 권한은 서버에서 판단한다. 생성된 예시는 스키마 연결 검증용이며 성능 평가셋이나 운영 정책으로 자동 승격하지 않는다.

## 사용자 제공 IT 티켓 개념 반영

아래는 사용자가 제공한 개념을 프로젝트 데이터 설계에 반영한 것이다. 링크의 본문을 이번 수정에서 독립적으로 검증한 것은 아니다.

- 제목: 문제나 요청을 구체적으로 요약한다.
- 배경 및 현재 상태: 사용자가 말한 증상·발생 시점·환경·영향 범위를 사실 중심으로 정리한다. 모르는 원인은 추측하지 않는다.
- 요청 내용: 필요한 지원을 명확하게 적는다. 실제 API의 필수 필드와 생성 조건은 서버 계약에 따른다.
- 담당자 및 진행 상태: 서버가 반환한 배정과 처리 결과를 설명한다. 생성 성공과 할당 성공을 구분한다.
- 해결 확인: 실제 지원 정책에 맞는 확인 결과를 기록한다. 모델이 임의의 완료 기준을 만들어 해결 처리하지 않는다.

개발/작업 티켓의 요구 사항·인수 시나리오는 기능 개발과 버그 수정의 검증 기준을 작성하는 패턴이다. 이를 모든 장애 티켓의 필수 필드로 가정하지 않는다. '1 티켓 = 1 변경'도 개발 작업 문맥이며 헬프데스크 접수 분할 규칙으로 자동 적용하지 않는다.

사용자 제공 참고 링크:

- [ServiceNow IT 티켓 시스템 설명](https://www.servicenow.com/kr/products/itsm/what-is-it-ticketing-system.html)
- [Zendesk 티켓 시스템 설명](https://www.zendesk.kr/blog/customer-service/ticketing-system/ticketing-system/)
- [사용자 제공 개발/작업 티켓 참고 글](https://yozm.wishket.com/magazine/detail/750/)

학습 대화에는 사용자 문의 → 부족한 정보 질문 → IT 티켓 내용 정리 → 생성 → 담당자 할당 → 상태 안내를 담는다. 권한 요청 사례를 추가한다면 접수·할당과 실제 권한 부여를 구분하며, 요청 접수가 승인이나 권한 부여를 의미하지 않도록 한다.

## 저장소 확인 후 판단 갱신

현재 코드에 assignee/할당 도구는 없다. 기존 6개 샘플은 가상 설계 예시이며 실제 런타임 계약으로 사용하지 않는다. 저장소 계획의 기준선 평가 60건, 튜닝 pilot 100~200건을 먼저 따르고 본문의 큰 수량은 확장 제안으로 본다. [확인 보고서](00_프로젝트_확인_및_재선정.md) 및 [제작 계획](12_RAG_자료와_튜닝_제작계획.md)을 우선한다.
