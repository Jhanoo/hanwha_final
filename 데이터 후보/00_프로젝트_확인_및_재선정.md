이전 대화의 Spring 서버는 향후 사용자 계획이다. 현재 저장소가 Spring 구현이라는 뜻으로 기록하지 않는다. 담당자에게 할당한다는 사용자 요구는 유지하지만, 현재 구현과 데이터 계약이 이미 갖춰졌다고 설명하지 않는다.

## 무엇을 학습해야 하는가

1. 한국어 장애 문의를 실제 분류 체계에 매핑한다.
2. 오류 메시지, 발생 시점, 환경, 영향 범위, 시도한 조치 중 부족한 정보를 질문한다.
3. 검색 문서에 근거해 안내하고, 해결되지 않으면 사실만 담은 티켓 초안을 만든다.
4. 승인 전 생성하지 않으며 결과를 받기 전에 접수 성공을 주장하지 않는다.
5. 담당자/지원팀 추천은 승인된 운영 규칙과 실제 후보 목록이 있을 때만 한다.
6. 반환된 티켓 상태와 처리 결과를 그대로 설명한다.

## 선정 결과

직접 도메인 자료는 Console-AI(문의/분류), Tobi-Bueck(분류/지원 큐), IT_Support_V2(검수할 증상 질문)다. 한국어 행동 보조는 ko-agentic-sft, 독립 평가는 FunctionChat-Bench를 유지한다.

다른 업무 도메인, 현재 튜닝 목적에 맞지 않는 이력 분석 자료, 중복되는 일반 도구 호출 후보는 목록과 샘플에서 제거했다. 유지한 공개 자료도 우리 담당자 목록과 정확한 배정 정답을 제공하지 않으므로 자체 규칙과 검수 대화가 필요하다.

## 튜닝 도입 시점

저장소 전략은 MVP에서 먼저 API 모델+RAG+prompt를 구축하고 fine-tuning을 미루는 방향이다. 이번 데이터 조사는 미래 실험 준비이며 전략 변경이나 모델 학습 승인이 아니다. 첫 기준선을 실행한 뒤 분류·추가 질문·요약·도구 선택의 반복 오류가 남으면 100~200건 pilot, 이후 300~1,000건의 검수 자료를 제안한다. 사전학습은 범위에서 제외한다.

학습용 ticket_draft와 실제 API body를 구분한다. 현재 POST /api/tickets는 title/priority/idempotency_key를 받고 category를 서버가 계산한다. LLM이 category/assignee를 출력해도 현재 API가 해당 값을 저장한다고 가정하지 않는다.
