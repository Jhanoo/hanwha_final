# 테스트·배포·데모 전달

프로젝트 루트 `AGENTS.md`와 커밋 규칙을 따른다. 사용자 요구와 기존 코드를 먼저 읽고, 현재 구현·계획·가정·검증 결과를 구분한다. 이 스킬은 현재 프로젝트를 위해 작성한 로컬 지침이다.

## 작업 순서

1. 요구사항 추적표에서 필수 검증을 선택하고 `docs/test-plan.md`에 정상·오류·권한·데이터 보존 시나리오를 적는다.
2. Python은 uv의 `.venv`로 실행한다. 기존 테스트가 있으면 사용하며 필요한 회귀 테스트만 추가한다.
3. UI는 수동 점검·Playwright CLI 또는 Python 자동화 중 작업에 맞는 방식을 선택한다. 두 방식을 동시에 강제하지 않는다.
4. Python 자동화에는 `webapp-testing`, 터미널 브라우저 조작에는 `playwright`를 읽는다. 패키지·브라우저가 없으면 필요한 의존성을 선언하고 설치·실행 여부를 구분한다.
5. DB와 티켓 API는 생성 → 조회 → 상태 변경 → 재시작 후 유지 및 잘못된 입력을 확인한다. 기존 사용자 데이터를 지우지 않는다.
6. CI를 요청받았으면 실제 선택한 테스트 명령과 uv 설치를 workflow에 반영한다. 실행하지 않은 CI를 통과로 표기하지 않는다.
7. 코드 검토는 요구사항 누락, 예외 처리, XSS, SQL 파라미터화, 비밀 값, 인증 경계를 우선한다.
8. 배포 대상이 정해지면 실행·환경 변수·영속 DB·health check·복구 절차를 `docs/runbook.md`에 작성하고 가능한 범위에서 검증한다. 공개 배포는 로컬 데모와 분리한다.
9. 발표 흐름은 상담 → 해결 안내 → 티켓 접수 → 담당자 처리 → 재시작 후 유지로 구성한다. 실제 연동과 모의 구현을 화면·설명에서 구분한다.

## 산출물 템플릿

[템플릿](references/template.md)을 필요한 부분만 사용한다. 요청받은 작업을 실행하고 결과를 검증한다. 이 템플릿 자체는 완성된 제품 문서나 실행 결과가 아니다.
