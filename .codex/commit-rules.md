# 커밋 메시지 규칙

이 프로젝트에서 작성하는 모든 커밋 메시지는 다음 규칙을 따른다.

- 항상 한국어로 작성한다. 고유명과 기술명(API, Controller, Repository, uv 등)은 영문 그대로 유지한다.
- Conventional Commits 형식을 따른다. type은 feat, fix, chore, docs, refactor, test, perf, style 등 변경 목적에 맞게 선택한다.
- 제목은 `<type>: <짧고 명확한 한글 요약>` 형식의 한 줄이며, type과 공백을 포함해 72자 이내로 작성한다.
- 제목과 본문은 변경 내용을 요약하는 명사형으로 작성한다. `추가`, `제공`, `수정`, `개선`, `반영`, `정리`, `제거`처럼 끝내고 마침표를 붙이지 않는다.
- `~하라`, `~해라`, `~하세요` 같은 명령형과 `~했습니다` 같은 서술형 종결은 사용하지 않는다.
- 제목 다음에 빈 줄을 하나 넣고, 본문은 3~5줄의 불릿 목록으로 핵심만 간결하게 요약한다.
- 불필요하게 긴 설명, 세부 구현 코드, 장황한 표현을 제외한다.
- 브레이킹 체인지가 있으면 본문 뒤에 `BREAKING CHANGE: <내용>`을 추가한다.
- 관련 이슈나 티켓이 있으면 마지막 줄에 `Refs: <번호|URL>`을 추가한다. 없는 번호나 URL을 만들지 않는다.
- Diff가 너무 작거나 의미가 불분명하면 억지로 커밋하지 않고, 간결한 한국어로 이유를 설명하고 적절한 커밋 단위를 제안한다.
- 사용자가 커밋 메시지 텍스트만 요청할 때는 설명, 서문, 코드블록 없이 메시지만 출력한다. 실제 작업 결과 보고까지 커밋 메시지 형식으로 제한하지 않는다.

## 예시

feat: 안테나 로그 API에 날짜 필터 추가

- API 및 Repository 쿼리에 날짜 필터 반영
- Service와 Controller에 날짜 파라미터 추가
- OpenAPI 스펙에 신규 파라미터 문서화
- 날짜 조건 처리 검증
