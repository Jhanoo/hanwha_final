## 출처와 상태

- PRD: [DeskMate PRD](prd.md), 초안 0.3
- 프로젝트 코드의 기존 규칙 기반 동작은 현재 구현, AI 기반 기능은 목표 요구사항으로 표기한다.
- P0는 AI 기술 시연 MVP의 필수 범위다.

## 수용 기준

### FR-001 상담 맥락

- Given 증상만 있고 조회 조건이나 기대값이 없는 수치 불일치 문의, When 직원이 질문하면, Then Agent가 조회 조건·기대값·실제값 중 부족한 항목을 묻는다.
- Given 증상·시점·영향이 모두 제공된 문의, When 상담하면, Then 이미 제공된 정보를 다시 묻지 않는다.
- Given 사용자 메시지에 비밀번호가 포함됨, When 이를 처리하면, Then 비밀번호를 되풀이하거나 저장하지 않고 안전 안내를 한다.

### FR-002·003 RAG

- Given 정답 문서가 색인된 장애 문의, When 검색하면, Then top-k 결과에 문서 ID·제목·구절이 포함된다.
- Given 검색 근거가 없는 문의, When 상담하면, Then Agent가 불확실성을 알리고 추가 정보 또는 담당자 이관을 제안한다.
- Given 답변, When 평가하면, Then 모든 해결 지침의 주장과 출처를 사례별로 대조할 수 있다.

### FR-004·005 티켓 승인

- Given 미해결 상담, When 요약이 준비되면, Then 사용자가 접수 전에 편집·확인할 수 있다.
- Given 사용자가 명시적으로 승인하지 않음, When 상담이 끝나면, Then 티켓 생성 호출은 0건이다.
- Given 사용자가 승인함, When 접수되면, Then 상담 ID·문제 분류·증상·시도한 조치와 source ID가 티켓에 저장되고 ID가 표시된다.

### FR-006·007 상태·중복

- Given 같은 상담 ID로 재시도, When 티켓 쓰기 도구가 호출되면, Then 기존 티켓 ID를 반환하고 중복 레코드를 만들지 않는다.
- Given 유효한 티켓, When 담당자가 상태를 변경하면, Then 새 상태와 변경 이력을 저장하고 조회에 반영한다.
- Given 없는 티켓 ID, When 상태 변경을 요청하면, Then 오류 응답을 반환하고 다른 레코드를 수정하지 않는다.

### FR-008·010 실패와 신뢰 경계

- Given LLM·검색·DB 중 한 요소가 실패함, When 요청을 처리하면, Then 구체적 내부 비밀 없이 fallback을 보여 주고 어떤 단계가 실패했는지 운영 trace로 식별한다.
- Given 문서나 메시지에 지침 탈취·데이터 유출 지시가 포함됨, When Agent가 검색·답변하면, Then 해당 텍스트를 사용자 콘텐츠로 인용할 뿐 추가 권한을 실행하지 않는다.

### FR-009 평가

- Given 고정 평가셋, When 동일 설정으로 평가를 실행하면, Then 사례 ID·모델 버전·문서 색인 버전·지표·실패를 재현 가능하게 저장한다.
- Then macro-F1, retrieval recall@3, 근거 일치율, 승인 없는 쓰기 횟수, tool schema 오류, 종단 간 완료율을 보고한다.

## 상태와 미결정 사항

- **현재 구현:** 규칙 기반 상담, PostgreSQL 티켓 생성·조회·상태 변경, 정적 UI.
- **미구현 목표:** 가상 매출 시스템·합성 조사 자료, Spring 제품 API·권한·Gateway·승인·배정, Python LLM/임베딩 retrieval, 근거 화면·담당자 보드, 평가 harness·통합 실행 패키지.
- **결정 필요:** 모델 이름, embedding model, 검색 chunk 크기·top-k, UI trace 노출 범위, Spring 버전·빌드 도구·내부 인증·migration 소유권. DB 검색은 PostgreSQL/pgvector이며 초기 schema는 1536차원이다.
- **보안 제한:** 실제 사내 데이터·계정 없이 synthetic dataset으로 시작.

- FR-013: Given 임의 SQL 또는 쓰기 요청, When 도구 호출, Then 실행을 거부하고 허용 범위 내 데이터만 반환한다.
- FR-014: Given 코드와 데이터 snapshot 불일치, When 조사, Then 불일치를 표시하고 원인을 확정하지 않는다.
- FR-015: Given 로그 조회 실패, When 진단 결과 생성, Then 코드/DB 정상이라고 단정하지 않고 실패한 단계와 미확인 사실을 기록한다.
- FR-016: Given 마지막 코드 작성자와 현재 소유 팀이 다름, When 배정, Then 현재 registry 팀을 사용한다. 팀이 없으면 미할당이다.
- FR-017: Given 조회 조건 오류, When 수정 후 기대값과 일치, Then 직원 확인 후 종료한다. Given 코드 수정 필요, Then 승인 후 전문 팀 이관을 제안한다.
- FR-018: Given 승인 전 초안 수정, When 접수, Then 변경된 hash에 대한 승인을 확인하고 이전 승인으로 생성하지 않는다.
- FR-019: Given 권한 거부 또는 조사 예산 초과, When 처리, Then 우회 호출이나 무한 재시도를 하지 않는다.

상세 도구 계약과 synthetic 수용 사례는 [시스템 진단 설계](investigation-design.md)를 따른다. 신규 요구사항은 현재 앱에 구현되지 않았다.

## 구현 산출물과 수용 확인

[완성 로드맵](implementation-plan.md)의 D-01~07을 기존 FR/NFR에 연결하며 별도 요구사항 번호를 중복 부여하지 않는다. [추적표](traceability.md)에 산출물별 연결을 유지한다.

- Given 고정 매출 snapshot과 WEB 조건, When FILTER-01을 수행하면, Then 80만 원과 전체 100만 원의 차이를 설명하고 직원 확인 후 티켓 없이 종료한다.
- Given 전체 조건에서 90만 원을 반환하는 오류 경로, When LOGIC-01을 수행하면, Then 정상 집계 100만 원과 코드·로그 근거를 초안에 담고 승인 후 현재 팀 티켓으로 연결한다.
- Given 담당자의 처리 기록, When 직원이 확인하면, Then 상태·처리 결과를 조회할 수 있다. 실제 수정·배포 여부와 직원 재조회 확인은 상태 변경과 별도로 기록한다.
- Given 자료/팀 정보가 없음, When UNKNOWN-01/OWNER-01을 수행하면, Then 원인을 확정하지 않거나 승인 후 미할당 큐로 접수한다.
- Given 팀원의 실행 환경, When 문서의 설정·migration·적재·시작 절차를 따르면, Then 두 대표 경로를 실행할 수 있고 재기동 후 티켓이 유지된다. 이는 앞으로 검증할 조건이다.
