# DeskMate PRD: 사내 IT 장애 대응 AI Agent

## 문서 상태

- 버전: 초안 0.1 · 기준일: 2026-10-08
- 목적: AI 기술 구현을 핵심 평가 대상으로 삼는 시연 프로젝트
- 확정 방향: 대화형 IT Agent, 근거를 보여 주는 RAG, 제한된 티켓 도구 호출, 재현 가능한 평가
- 모델 선택안: 호스팅 LLM API `gpt-4.1-mini` 후보 + pgvector RAG. Fine-tuning은 기준선 평가 전 보류
- 가정: 시연은 synthetic 사내 IT 문서와 가상 직원 문의를 사용한다. 실제 사내 자료·시스템·인증은 제공되지 않았다.
- 미결정: 모델 후보의 API 계정·지역 가용성 및 최신 가격 확인, API 인증, 발표 시간, 심사 rubric

## 문제와 목표

직원은 VPN, 계정, 메일 같은 장애가 생기면 적절한 해결 문서와 지원 창구를 찾기 어렵다. 기존 챗봇은 키워드 안내에 그쳐 자연어 증상 파악, 답변 근거 제시, 상담 맥락을 담은 담당자 이관을 보여 주지 못한다.

**목표:** 자연어 장애를 분류하고, 사내 IT 지식 검색 근거를 인용해 안내하며, 해결되지 않은 상담만 직원 확인 후 티켓으로 구조화해 넘기는 AI Agent를 시연한다. 검색·모델·도구 호출을 화면과 평가 결과에서 각각 확인할 수 있게 한다.

**대상 사용자:** IT 지원을 요청하는 직원, 상담 티켓을 검토·처리하는 담당자, Agent 품질을 확인하는 프로젝트 심사자.

## 핵심 시나리오

1. 직원이 “오늘 아침부터 VPN 접속 후 사내 파일 서버가 안 열려요”라고 묻는다.
2. Agent는 증상 파악에 필요한 질문을 하고, 개인정보나 비밀번호를 묻지 않는다.
3. 지식 검색 결과에서 관련 VPN 문서를 찾아 문서 제목과 근거 구절을 표시한다.
4. 직원이 조치 후 미해결을 선택하면 Agent가 증상·영향·시도한 조치·검색 근거를 요약한다.
5. 직원이 티켓 내용을 확인하고 접수에 동의하면 티켓 생성 도구를 한 번 호출한다. Agent는 생성된 티켓 ID를 알려 준다.
6. 담당자가 티켓 상태를 변경하고 직원 화면에서 처리 현황을 확인한다.
7. 검색 근거가 없거나 모델·도구가 실패하면 모르는 내용을 지어내지 않고 담당자 연결을 제안한다.

| PRD-001 | 상담 맥락 수집 | P0 | VPN·계정·메일 증상에서 핵심 정보가 부족하면 구체적 확인 질문 제시 |
| PRD-002 | 사내 지식 RAG | P0 | 관련 synthetic 문서 검색, 관련 문서·구절 표시, 근거 없는 답변 제한 |

| PRD-004 | 직원 승인 후 티켓 이관 | P0 | 접수 전 요약 확인, 확인 없이 쓰기 도구를 실행하지 않음, 티켓 ID 표시 |
| PRD-005 | 담당자 티켓 처리 | P0 | 티켓·대화 요약·출처 확인, 상태 변경, 변경 결과 반영 |
| PRD-006 | 실패와 fallback | P0 | 검색 0건, 모델 오류, 도구 timeout·중복에서 안전한 안내 및 추적 정보 표시 |
| PRD-007 | Agent 평가 | P0 | 고정 테스트셋에서 검색·근거·질문·도구·이관 지표와 개별 사례 확인 |

## 범위와 단계

- **현재 기준선:** Python HTTP 서버, 정적 HTML UI, 키워드 규칙 상담, PostgreSQL + pgvector DB와 티켓 API. LLM·embedding ingestion·RAG는 미구현.
- **MVP 목표:** OpenAI Agents SDK를 이용한 단일 IT 지원 Agent, PostgreSQL + pgvector의 임베딩 검색 RAG, 명시적 승인 경계가 있는 티켓 함수 도구, 평가 harness와 시연 대시보드. LLM은 우선 호스팅 API 후보로 구현하고 fine-tuning은 하지 않는다.
- **MVP 데이터:** VPN·계정·메일 관련 가상 사내 가이드와 가상 장애 시나리오. 실제 계정·직원·네트워크 정보를 사용하지 않는다.
- **제외:** Jira/ServiceNow 실서비스 쓰기, 여러 Agent 자율 협업, 실제 사내 문서 수집, 직원 인증/권한 체계, 음성, 프로덕션 배포. 별도 요구가 확인되면 재검토한다.

## AI 기술 시연 포인트

- **RAG:** 문서 분할과 metadata, 검색 top-k, 답변의 근거 문서·구절, 검색 점수/실패 사례.
- **Agent:** 명확한 입력·출력 스키마가 있는 검색·상담 요약·티켓 도구 및 실행 trace.
- **사람 승인:** 읽기 도구와 쓰기 도구를 구분하고 티켓 생성 직전에 사용자 확인.
- **신뢰성:** 검색 근거 없음, 불확실한 진단, LLM 장애와 티켓 중복에 대한 fallback.
- **평가:** RAG retrieval recall@k, 답변 근거 일치, 분류·추가 질문 정확도, 도구 선택·인자 정확도, 승인 규칙 준수, 종단 간 완료율, 지연·토큰 비용.

## 시연용 성공 목표

다음 수치는 실측값이 아니라 **MVP 수용을 위한 제안 목표**다. 평가셋 작성 후 확정하고 결과를 함께 공개한다.

- 고정된 60개 synthetic 문의(개발용 40개, holdout 20개) 중 증상 분류 macro-F1 ≥ 0.80.
- 정답 문서가 있는 사례에서 top-3 검색 recall ≥ 0.85.
- 생성 답변이 근거 문서에 의해 뒷받침되는 비율 ≥ 0.90. 근거 부족 사례에서 무근거 해결 안내 0건.
- 티켓 생성 tool schema 유효성 ≥ 0.95, 확인 없는 티켓 생성 0건.
- 대화에서 접수·담당자 상태 변경까지 이어지는 종단 간 시연 3회 연속 성공.

수치는 작은 시연 데이터셋의 운영 품질 보증이나 실제 사내 서비스의 성능 보장을 뜻하지 않는다.

모델 후보와 학습 데이터, 튜닝 전환 기준은 [LLM 선택과 데이터 전략](llm-strategy.md)을 따른다.

## 제약과 위험

- API key와 모델 비용, 네트워크가 필요할 수 있다. key는 환경 변수로만 제공하며 채팅·Git·로그에 출력하지 않는다.
- synthetic 지식 문서도 검색 품질·인용 정합성 검토가 필요하다. 문서의 허위 정보를 생성하지 않는다.
- 개인정보·프롬프트 인젝션·환각·부적절한 티켓 생성을 위협 시나리오와 테스트에 넣는다.
- 현재 로컬 데모에는 인증이 없으며 운영 환경으로 노출하지 않는다.

## 발표 흐름

1. 시스템 구성도와 평가 데이터셋 소개.
2. VPN 문의를 입력하고 Agent의 추가 질문 확인.
3. RAG 문서 근거와 Agent trace를 확인하며 해결 가이드 제공.
4. 미해결 선택 후 상담 요약 수정·확인.
5. 승인 후 티켓 도구 실행, 티켓 생성 결과 확인.
6. 담당자가 상태를 변경하고 직원 화면에서 반영 확인.
7. 무관 문의 또는 검색 실패 예시에서 무근거 답변을 거부하고 이관하는 안전 동작 시연.
8. 평가 지표, 실패 사례, 현재 기준선과 구현된 범위를 발표.
