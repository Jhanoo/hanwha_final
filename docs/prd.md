# DeskMate PRD: 사내 시스템 장애 진단 및 담당자 연결 AI Agent

## 문서 상태

- 버전: 초안 0.2 · 기준일: 2026-10-08
- 사용자 결정: 직원의 시스템 문제를 조사하고, 직접 해결 가능한 조치를 안내하거나 담당 팀으로 연결한다.
- 목표 구성: Spring Boot 업무 백엔드 + Python AI Service + OpenAI API 후보 + PostgreSQL/pgvector.
- 현재 구현: Python 규칙 상담과 PostgreSQL 티켓 데모. 아래 진단·Spring·AI·배정 기능은 목표다.
- 전제: 실제 사내 시스템 접근 없이 가상 업무 시스템과 검수한 합성 자료로 시연한다.

## 문제와 목표

직원이 수치 불일치, 조회 오류, 권한 오류 등을 발견해도 필요한 확인 항목과 담당 팀을 알기 어렵다. 지원 담당자는 접수 후 같은 정보를 다시 수집하고 시스템·로그·코드를 찾아야 한다.

목표는 **문제 파악 → 근거 조사 → 직원이 수행 가능한 해결 안내 → 미해결 또는 전문 조치 필요 시 승인 후 담당 팀 이관 → 상태 추적**이다. 확인된 사실과 원인 후보를 구분하고, 조사 내용을 티켓에 전달해 반복 질문을 줄인다. 절감 효과는 실제 측정 전 주장하지 않는다.

‘스스로 해결’은 직원이 검증된 안내를 따라 해결하는 것으로 정의한다. AI의 데이터 수정·코드 변경·배포는 MVP에 포함하지 않는다.

## 핵심 시나리오

직원이 “DB 조회 수치가 틀립니다”라고 문의한다. Agent는 화면/서비스, 조회 조건·시점, 기대값과 실제값을 묻는다. 예시 업무는 가상 주문 매출 조회다.

1. 정의 문서에서 매출의 기준(기간, 시간대, 주문 상태, 할인/취소 포함)을 찾는다.
2. 허용된 조회 템플릿으로 원천 합계와 API 결과를 비교한다.
3. 해당 요청의 로그, 실행된 코드 버전, API→함수 매핑을 확인한다.
4. 정상 데이터와 불일치한 집계 코드가 확인되면 근거를 제시하고 원인 후보를 기록한다. 증거가 부족하면 추가 확인이 필요하다고 설명한다.
5. 조회 조건 오류라면 직원이 조건을 수정해 해결하도록 안내한다. 코드 수정이 필요하면 현재 서비스 소유 팀에 이관할 초안을 만든다.
6. 직원 승인 후 Spring이 티켓을 생성하고 검증된 담당 팀에 배정한다. 담당 팀이 불명확하면 미할당 큐로 접수한다.
7. 담당자가 처리 결과를 기록하고 직원이 해결 여부를 확인한다.

## MVP 기능

| ID | 기능 | 완료 기준 |
|---|---|---|
| PRD-001 | 상담 맥락 수집 | 서비스·환경·시점·조건·기대값·실제값 중 누락된 필수 정보만 질문 |
| PRD-002 | 지식 RAG | 업무 정의·조치 가이드·서비스 문서를 출처와 버전으로 검색 |
| PRD-003 | Agent 도구 및 초안 | 도구 선택·입력·결과와 사실 기반 티켓 초안 기록 |
| PRD-004 | 승인 후 이관 | Spring이 초안 hash·권한·승인·멱등성을 검증한 뒤 생성 |
| PRD-005 | 담당자 처리 | 담당자가 조사 요약·근거·재현 조건을 보고 상태/결과 기록 |
| PRD-006 | 실패 대응 | 권한 거부·조회 실패·불명확한 생성 결과를 성공으로 설명하지 않음 |
| PRD-007 | 평가 | 고정 사례로 질문·검색·조사·이관·권한 준수 결과 기록 |
| PRD-008 | 읽기 전용 시스템 조사 | 허용된 DB 집계·로그·코드 조회를 수행하고 관측 시점/버전을 기록 |
| PRD-009 | 근거 기반 원인 후보 | 관측 사실·가설·미확인 정보·다음 행동을 구분해 반환 |
| PRD-010 | 서비스 소유 팀 연결 | 유효한 소유권 목록으로 팀 추천·배정; 미등록 시 미할당 안내 |

## 범위와 우선순위

- P0: 가상 주문 매출 시스템 하나, 수치 불일치 사례, 문서 RAG, 제한된 DB/로그/코드 도구, 초안 승인, 팀 배정, 상태 추적.
- P0 정상/실패 유형: 직원 조회 조건 오류, 업무 코드 집계 오류, 근거 부족·접근 거부.
- P1: 원천 데이터 이상, 일시적 서버 오류, 권한 문의와 추가 업무 시스템. 각 연결·정책을 검증한 후 확장한다.
- 제외: 임의 SQL 실행, DB 수정, 자동 코드 수정·배포, 실제 직원으로 알림 발송, 전사 자율 조사, 다중 Agent, 초기 fine-tuning.
- 담당자는 Git 최초 작성자가 아닌 현재 서비스 소유 팀을 우선한다. Git 이력은 코드 변경 근거다.

## 데이터와 성공 기준

가상 주문/조회 결과, 배포 코드 snapshot, 관련 로그, 업무 정의·조치 문서, 서비스/API/코드 매핑, 담당 팀 목록을 동일 scenario ID와 버전으로 연결한다. 공개 상담 후보는 표현·분류 보조용이며 이 시스템의 정답을 대신하지 않는다.

기존 계획의 60개 사례(개발 40, holdout 20)를 유지한다. 원본 시나리오·템플릿·코드 결함 변형은 같은 분할에 배치한다. 근거 없는 원인 확정, 승인 없는 티켓 생성, 허용되지 않은 조회, 중복 생성, 존재하지 않는 담당자 배정은 0건을 제안 목표로 둔다. 질문 효율·검색·이관·지연·비용은 사례별로 기록하고 실측 후 수용 목표를 확정한다.

## 발표 흐름

1. 같은 문의에 조회 조건 오류와 코드 오류 두 가지 fixture를 제시한다.
2. 추가 질문 → 문서 근거 → DB/로그/코드 조회를 화면에 표시한다.
3. 첫 사례는 직원이 조건을 수정해 해결하고 상담을 종료한다.
4. 두 번째는 확인 사실·원인 후보·담당 팀·재현 조건이 담긴 초안을 승인해 접수한다.
5. 담당 팀 처리 및 상태 반영, 권한 거부/근거 부족 사례를 보여 준다.

상세 계약·fixture·조사 범위는 [시스템 진단 설계](investigation-design.md), 모델·학습 전략은 [LLM 전략](llm-strategy.md)을 따른다. 일정, 실제 사내 연동, 모델 가용성·가격과 담당자 운영 정책은 미확정이다.

사용자 역할, 합성 주문 데이터, 대표/예외 시나리오와 발표 준비 항목은 [페르소나·시나리오·데모 가정](personas-and-demo-scenarios.md)을 참고한다. 문서의 가정은 실제 구현이나 실행 결과를 의미하지 않는다.
