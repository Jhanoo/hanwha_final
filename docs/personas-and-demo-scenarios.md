# DeskMate 페르소나·시나리오·데모 가정

기준일: 2026-10-08. 이 문서는 [PRD](prd.md)와 [시스템 진단 설계](investigation-design.md)를 구체화한 발표·구현 준비 자료다. 이름, 회사, 업무 데이터, 담당 팀은 모두 합성 설정이며 아래 진단 기능은 목표다. 현재 실행 가능한 제품은 Python 규칙 기반 상담과 PostgreSQL 티켓 데모다.

## 1. 사용자 페르소나

| 페르소나 | 업무·상황 | 필요와 불편 | DeskMate에서 하는 일 | 성공 조건 |
|---|---|---|---|---|
| 김하늘 · 매출 운영 직원 | 일별 매출을 조회해 보고서를 작성. SQL·코드 분석은 익숙하지 않음 | 수치 차이의 이유와 문의할 팀을 모름. 반복 설명 없이 업무를 재개하고 싶음 | 증상·조회 조건·기대/실제값 제공, 안내 수행, 해결 확인, 티켓 초안 수정·승인 | 조건 오류는 스스로 해결. 전문 조치가 필요하면 재현 정보가 담긴 티켓으로 연결 |
| 이도현 · 판매시스템 개발 담당자 | 현재 판매시스템 팀의 티켓을 처리 | ‘수치가 이상함’만으로는 재현이 어려움. 조건·로그·실행 코드 버전을 다시 수집해야 함 | 배정된 티켓의 근거·미확인 항목 확인, 재현·수정 판단, 처리 결과와 상태 기록 | 같은 질문을 반복하지 않고 조사 시작. Agent의 가설을 근거와 대조 가능 |
| 박서윤 · IT 지원 관리자 | 서비스 소유 팀 목록과 미할당 큐 관리 | 담당 팀 변경·정보 누락·잘못된 배정으로 이관이 지연됨 | 소유권 목록 확인, 미할당 티켓 배정·재배정, 예외 처리 | 존재하지 않는 담당자에게 배정하지 않고 접수된 요청을 추적 |

AI는 사용자 페르소나 대신 시스템 역할이다. 질문·읽기 조사·근거 정리·이관 제안을 수행하며, 최종 권한 판단과 티켓 쓰기는 Spring이 담당한다. 첫 MVP는 팀 단위 배정을 사용한다. 개인 담당자 지정은 해당 팀의 관리자 선택으로 확장할 수 있다.

## 2. 데모를 위한 공통 상황 가정

| 항목 | 가정 | 데모에서 보여 줄 것 |
|---|---|---|
| 회사·업무 | 가상 회사 ‘데모상사’의 매출 운영 업무 | 실제 사내 시스템이라고 소개하지 않음 |
| 조사 대상 | 가상 `sales-demo` 시스템의 ‘일별 매출 조회’ 화면과 조회 API | 같은 기능에서 조건 오류/코드 오류를 비교 |
| 직원 지식 | 직원은 화면을 사용할 수 있지만 DB 접근이나 코드 변경 권한은 없음 | 일상 표현을 서비스·기간·조건·값으로 구체화하는 질문 |
| 지표 정의 | 기준 시간대 Asia/Seoul, 원화, PAID/FULFILLED 주문의 결제금액 합계, 취소 제외 | 검색된 업무 정의 문서와 버전 표시 |
| 금액 단순화 | 아래 fixture는 할인·부분 환불·세금 차이 없음. 금액은 정수 원 단위 | 복잡한 정산 규칙으로 진단 범위를 확대하지 않음 |
| 조회 기간 | 2026-10-07 00:00 이상, 2026-10-08 00:00 미만(KST) | 비교하는 DB/API에 동일 조건 적용 |
| 관측값 | 문의 시점은 2026-10-08 오전. 각 시나리오는 고정 snapshot 사용 | 서로 다른 시점의 데이터를 비교해 원인을 단정하지 않음 |
| 시스템 매핑 | `sales-demo` → 일별 매출 endpoint → 배포 commit → 허용된 집계 함수가 등록됨 | Agent가 알 수 없는 시스템 경로를 만들어내지 않음 |
| 소유 팀 | `TEAM-SALES` = 현재 판매시스템 팀, 관리자 박서윤이 registry 관리 | 코드 작성자와 현재 소유 팀을 구분 |
| 지식 자료 | 업무 정의, 화면 사용법, 조건 점검, 전문 조치 기준의 검수된 가상 문서 | 출처·문서 버전·적용 범위 표시 |
| 조사 권한 | 직원에게 허용된 매출 집계·마스킹 로그·등록 코드 근거만 Spring Gateway가 제공 | 원시 고객정보·암호·임의 SQL 없이 조사 |
| 연결 경계 | DeskMate 저장 DB와 조사 대상 업무 DB는 논리적으로 별도 | 상담/티켓 저장과 업무 데이터 조회를 구분 |
| 접수 승인 | 직원이 확인한 초안에만 서버 승인 ID·hash·멱등 키를 적용 | 초안 생성과 실제 티켓 생성의 차이 |
| 배정 정책 | 등록된 현재 팀을 우선 배정. 미등록/충돌 시 미할당 큐 | 없는 직원 이름이나 팀을 생성하지 않음 |
| 자동 조치 | 직원의 조회 조건 수정은 가능. 데이터 수정·코드 배포는 담당자가 수행 | Agent가 자동으로 코드 결함을 고쳤다고 설명하지 않음 |
| LLM·검색 | OpenAI API 후보와 pgvector를 사용하도록 설계. 호출·색인은 구현 후 확인 | 실시간 모델 결과와 준비된 fixture/영상/모의 응답을 명시적으로 구분 |

이 표는 실제 연결 완료 목록이 아니다. 계정·권한, 진단 도구, 업무 화면/API, 코드 snapshot, 로그, owner registry는 제작·구현이 필요하다.

## 3. 공유 합성 주문 데이터 설계

snapshot 이름은 예시 식별자 `sales-snapshot-v1`이다. 실제 파일·DB snapshot은 아직 없다. 주문 상태는 업무 주문의 상태이며 티켓의 open/in_progress/resolved와 별개다.

| 주문 ID | 주문 상태 | 채널 | 결제금액 | 결제 시각(KST) | 전체 채널 지표 포함 |
|---|---|---|---:|---|---|
| ORDER-001 | PAID | WEB | 400,000원 | 2026-10-07 09:00 | 포함 |
| ORDER-002 | PAID | WEB | 300,000원 | 2026-10-07 10:00 | 포함 |
| ORDER-003 | PAID | STORE | 200,000원 | 2026-10-07 11:00 | 포함 |
| ORDER-004 | FULFILLED | WEB | 100,000원 | 2026-10-07 12:00 | 포함 |
| ORDER-005 | CANCELLED | WEB | 150,000원 | 2026-10-07 13:00 | 제외 |

정답 합계는 **1,000,000원**이다. WEB만 조회하면 **800,000원**, 모든 채널에서 PAID만 집계하면 **900,000원**이다. 취소된 금액을 포함한 단순 합계 1,150,000원을 매출 정답으로 취급하지 않는다.

각 fixture는 지표 정의 버전, DB snapshot, 입력 조건, API 응답, request ID, 배포 commit, 코드 구절, 로그, 소유 팀 버전을 함께 기록한다. 배포 commit과 request ID는 구현 후 실제 fixture에서 생성하며 지금 임의의 실행 성공 근거로 만들지 않는다.

## 4. 주 시나리오 A — 직원이 직접 해결

- ID: FILTER-01 / 대상: 김하늘
- 상황: 직원은 전체 채널 매출 1,000,000원을 기대하지만 화면에 WEB 필터가 적용돼 800,000원이 표시된다.
- 목표: 단순 조건 차이를 코드 오류로 오인하지 않고 직원 조치로 해결.

| 단계 | 직원·시스템 행동 | 보여 줄 근거·결과 |
|---|---|---|
| 문의 | 직원: “매출 조회 수치가 틀립니다.” | 불완전한 최초 문의 |
| 추가 질문 | Agent: “어떤 화면이고, 조회 기간·채널·기대값과 실제값은 어떻게 되나요?” | 누락된 필수 정보만 질문 |
| 정보 제공 | 직원: “10월 7일 일별 매출입니다. 전체 100만 원으로 알고 있는데 80만 원이에요. 채널은 WEB입니다.” | 기간·필터·기대값·실제값 구조화 |
| 정의·값 확인 | 문서 검색 후 `inspect_metric`으로 전체/WEB 합계를 비교 | 정의 문서, snapshot, 전체 100만 원·WEB 80만 원 |
| 안내 | Agent: “현재는 WEB만 조회해 STORE 주문 20만 원이 제외됐습니다. 전체 채널로 변경해 다시 조회해 주세요.” | 관측값에 근거한 조치. 필요 없는 코드 조회는 생략 |
| 해결 확인 | 직원이 조건을 바꾸고 “100만 원으로 나옵니다”라고 확인 | 실제 재조회가 구현되면 결과도 확인. 직원 진술만이면 그 사실을 구분 |
| 종료 | 해결 내용 기록 후 상담 종료 | 티켓 생성 0건 |

금지 동작: DB/코드 결함을 단정하거나 데이터를 고치도록 안내, 사용자가 해결했다고 말하기 전에 완료 선언.

## 5. 주 시나리오 B — 조사 후 담당 팀으로 연결

- ID: LOGIC-01 / 대상: 김하늘 → 이도현(판매시스템 팀)
- 상황: 기간·전체 채널 조건은 맞지만 API 집계가 PAID만 포함하고 유효한 FULFILLED 주문 100,000원을 제외한다.
- 목표: 근거를 담은 전문 조치 이관과 승인·배정을 시연.

| 단계 | 직원·시스템 행동 | 보여 줄 근거·결과 |
|---|---|---|
| 문의 | 직원: “매출 조회 수치가 틀립니다.” | A와 같은 표현이 다른 원인으로 이어짐 |
| 추가 질문 | 직원: “10월 7일 전체 채널입니다. 기대값 100만 원, 화면은 90만 원입니다.” | 조회 조건이 충분하면 반복 질문하지 않음 |
| 데이터 비교 | 문서 정의와 허용된 원천 집계, 해당 API 응답 비교 | 같은 snapshot에서 정답 100만 원 / 실제 90만 원 |
| 코드·로그 확인 | 관련 요청 로그와 실제 배포 commit의 집계 코드 조회 | PAID만 포함한 조건, 누락된 ORDER-004 10만 원, 실행 경로 |
| 조사 요약 | Agent: “집계 로직이 FULFILLED 주문을 제외한 것이 차이의 원인 후보입니다. 코드 수정은 담당 팀 확인이 필요합니다.” | 사실·가설·미확인 항목 분리. 재현까지 검증한 경우만 확정 표현 |
| 소유 팀 조회 | `get_service_owner`가 현재 `TEAM-SALES`를 반환 | registry 버전·유효 기간. 최초 작성자가 달라도 현재 팀 선택 |
| 초안 검토 | 직원에게 재현 조건·기대/실제값·근거·현재 팀을 표시 | 아직 티켓 없음 |
| 수정·승인 | 직원이 초안을 확인 또는 수정하고 ‘접수 승인’ | 수정 시 새 hash에 대해 승인 |
| 생성·배정 | Spring이 검증 후 티켓 생성, TEAM-SALES 배정 결과 반환 | 실제 생성된 ticket ID. 생성/배정 성공을 구분 |
| 담당자 처리 | 이도현이 근거와 재현 조건을 검토하고 처리 중으로 변경 | 담당자 보드에 조사 요약 전달 |
| 처리 결과 | 담당자가 별도로 수정·검증한 결과를 기록하고 직원이 재조회·확인 | 수정을 실제로 수행했는지 모의 처리인지 표시. 상태 클릭만으로 수정 완료 주장 금지 |

### 티켓 초안 예시

- 제목: 일별 매출 조회에서 FULFILLED 주문 금액 누락 의심
- 서비스/화면: sales-demo / 일별 매출
- 재현 조건: 2026-10-07(KST), 전체 채널, sales-snapshot-v1
- 기대/실제: 1,000,000원 / 900,000원
- 확인 사실: 업무 정의는 PAID/FULFILLED 포함, 원천 집계 100만 원, API 결과 90만 원
- 원인 후보: 실행 집계 로직의 PAID 단독 조건으로 ORDER-004 제외
- 근거: 실제 제작할 문서·조회 결과·request ID·배포 commit·코드 위치 참조
- 영향: 해당 조건의 일별 매출 보고가 10만 원 낮게 표시. 다른 날짜·사용자 영향은 미확인
- 시도한 조치: 기간/채널 확인 및 재조회. 직원이 하지 않은 조치는 추가하지 않음
- 요청: 담당 팀이 집계 조건을 확인하고 수정 여부 판단
- 배정 후보: TEAM-SALES. Spring이 생성 시 유효성 재검증

금지 동작: AI가 코드/DB를 변경, 모든 DB 데이터가 정상이라고 일반화, 담당자 응답 전 수정 완료 안내, 승인 전 접수.

## 6. 보조·예외 시나리오

| ID | 가정 | 기대 행동 | 보여 줄 핵심 |
|---|---|---|---|
| UNKNOWN-01 | 로그 또는 배포 commit 확인 불가 | 확인된 값과 실패한 조사 단계만 설명, 원인 미확정 티켓 제안 | 근거 부족을 인정하는 진단 |
| DENIED-01 | 다른 부서 데이터나 허용되지 않은 원시 주문 요청 | 권한 거부 안내, 우회 조회 금지. 필요하면 권한 문의 접수 제안 | 읽기 도구의 권한 경계 |
| OWNER-01 | 현재 팀 정보 없음/충돌 | 티켓을 미할당 큐로 생성하고 관리자 배정 | 책임자를 생성하지 않는 동작 |
| APPROVAL-01 | 직원이 초안 승인을 거부 | 초안 보존 또는 상담 종료, 티켓 생성 0건 | 사람 승인 경계 |
| RETRY-01 | 생성 후 응답 유실로 같은 요청 재시도 | 멱등 키로 기존 ID 확인, 중복 생성 금지 | 접수 결과 복구 |
| ASSIGN-01 | 티켓 생성 성공, 팀 배정 실패 | 실제 ticket ID와 미할당 상태 안내, 생성 반복 금지 | 생성과 배정의 분리 |

최초 발표는 A·B를 중심으로 하고 UNKNOWN-01 또는 OWNER-01 하나를 선택해 예외를 보여 준다. 나머지는 평가·질의응답용으로 준비한다.

## 7. 발표 진행안

아래 시간은 **약 7분을 가정한 제안**이며 실제 발표 시간은 미정이다.

| 구간 | 발표 행동 | 관객이 확인할 것 |
|---|---|---|
| 0:00–0:45 | 가상 회사·사용자·현재/목표 상태 및 구조 소개 | Spring 권한/티켓, Python 조사, RAG와 실제 조회 차이 |
| 0:45–2:15 | FILTER-01 문의·추가 질문·근거·조건 수정 | 직원이 해결하는 경로와 불필요한 이관 방지 |
| 2:15–4:45 | LOGIC-01 동일 문의·DB/로그/코드 조사·초안 검토·승인 | 도구 선택, 사실/가설 구분, 현재 소유 팀 연결 |
| 4:45–5:45 | 담당자 보드·배정·상태·처리 내용 확인 | 조사 맥락이 담당자에게 전달됨 |
| 5:45–6:30 | 근거 부족 또는 소유 팀 미등록 사례 | 무근거 확정·허위 담당자 없이 처리 |
| 6:30–7:00 | 실제 실행 범위와 평가·한계 공개 | 관측한 결과와 아직 미구현인 부분 구분 |

Agent 대화 문장은 예시이며 실제 응답 문자열 일치를 평가하지 않는다. 내용·근거·호출·승인 동작을 확인한다. 준비된 fixture의 정답을 프롬프트에 몰래 넣어 실제 도구 조사인 것처럼 시연하지 않는다.

## 8. 시연 전 준비할 산출물

| 산출물 | 구체 내용 | 현재 상태 |
|---|---|---|
| 합성 업무 데이터 | 위 주문 5건, 동일 기간/필터의 정답 집계 | 문서 설계만 있음 |
| 가상 업무 화면/API | 정상 필터 경로와 LOGIC-01 오류 집계 경로 | 미구현 |
| 문서 corpus | 지표 정의·화면 사용법·조치·이관 기준, 출처·버전 | 제작 필요 |
| 코드·로그 fixture | 배포 commit에 맞는 함수·request log·API 매핑 | 제작 필요 |
| 소유권 registry | service ID, component ID, team ID, 유효 기간 | 제작 필요 |
| 데모 identity | 직원·담당자·관리자 권한, 접근 범위 | 미구현 |
| Spring Gateway | 등록 query·로그·코드·소유 팀 조회, 권한·예산 검증 | 미구현 |
| Python AI/RAG | 모델·임베딩·문서 검색·도구 선택·조사 요약 | 미구현 |
| 승인·팀 배정 UI/API | 초안 검토·승인·현재 팀 배정·미할당 큐 | 미구현; 기존 티켓·상태 데모만 있음 |
| 평가·시연 증거 | 고정 사례·gold evidence·실행 trace·결과 | 제작·실행 필요 |

각 실행에 scenario ID, fixture/index/model/code 버전을 고정하고 사용한 실제 request/ticket ID를 기록한다. 재시연은 별도 demo dataset/namespace로 준비해 기존 사용자 티켓을 지우지 않는다. 네트워크 실패 시 녹화 또는 mock을 사용할 수 있지만 실시간 LLM 실행과 구분해 표시한다.

## 9. 가정으로도 대신할 수 없는 동작

데모 회사·데이터·팀 이름은 가상으로 설정해도 된다. 반면 도구 호출 여부, 권한 거부, 실제 티켓 생성, 멱등 처리, RAG 근거 반환은 해당 기능을 구현·검증해야 시연 성공으로 설명할 수 있다. 고정 로그/코드 fixture 조사는 외부 운영 시스템 실시간 연동과 구분한다.

설계 단계인 현재에는 위 동작의 완료율·시간 절감·정확도를 주장하지 않는다. 구현 후 고정 평가 결과와 사례별 실패를 함께 기록한다.
